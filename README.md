# Multi-Clinic Scheduling System

A DBMS mini project for coordinating patients, doctors, clinics, rooms, equipment, appointments, clinical notes, prescriptions, medicines, and follow-ups. MySQL remains the source of truth for transactional data; ChromaDB is an optional retrieval index for authorized clinical-note search.

## Architecture

`Next.js` -> `FastAPI` -> `MySQL`  
                              -> `ChromaDB` + `sentence-transformers`

The database entities follow the supplied course schema: `DOCTOR`, `CLINIC`, `PATIENT`, `MEDICINE`, `DOCTOR_AVAILABILITY`, `DOCTOR_CLINIC`, `ROOM`, `EQUIPMENT`, `APPOINTMENT`, `APPOINTMENT_EQUIPMENT`, `CLINICAL_NOTE`, `PRESCRIPTION`, `PRESCRIPTION_MEDICINE`, and `FOLLOW_UP`. The PDF was found in the adjacent course directory and was used as the design baseline; the SQL keeps these names and relationships.

## Setup

1. Copy `.env.example` to `.env` and set a MySQL database URL and a long `JWT_SECRET`.
2. Initialize MySQL with `database/schema.sql`, then load `database/seed.sql`.
3. Backend:

   ```powershell
   cd backend
   python -m venv .venv
   .\.venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   uvicorn app.main:app --reload
   ```

4. Frontend:

   ```powershell
   cd frontend
   npm install
   npm run dev
   ```

5. Run backend tests with `pytest backend/tests -q`. Set `DATABASE_URL` to a test database for integration tests.

The `APP_USER` table stores application accounts. Public registration creates
clinic-scoped `STAFF` accounts only; create the first `ADMIN` by inserting a
bcrypt hash generated by `backend/app/auth.py` or through an existing
administrator. Never commit a real password or secret. No real patient
information is included.

## API

Interactive documentation is available at `/docs`. Important routes include
`POST /auth/register`, `POST /auth/login`, `GET /auth/me`, ADMIN-only
`/users` management, `GET /dashboard`, `GET /appointments`,
`POST /appointments`, `GET/POST /notes`, and `POST /notes/search`.

Appointment creation locks the doctor, room, and requested equipment rows inside one transaction, checks availability and overlapping non-cancelled appointments, and only then inserts the appointment. Conflicts return HTTP 409.

Appointment and clinical-note identifiers are generated by MySQL
`AUTO_INCREMENT` columns. Scheduling also checks the doctor's weekday
availability and requested time range before checking resource overlaps.
The backend regression suite can run without a database; live MySQL
connectivity and SQL feature execution require a configured disposable MySQL
8.0.16+ instance.

## Semantic search

`vector_store/sync.py` indexes eligible note text using `all-MiniLM-L6-v2` (384-dimensional embeddings) and stable SQL note IDs. Chroma uses cosine distance and a configurable top-k. Search results are resolved back through MySQL and authorized by the requesting user's role and clinic. Missing Chroma or model services produce an explicit 503 rather than exposing unverified results. Updated notes are upserted; deleted notes can be removed with the synchronization utility.

## Scope and future work

This deliverable includes the transactional backend, schema objects, authorization, semantic-search adapter, and a connected Next.js dashboard. Production deployment should add managed secrets, TLS, migrations, audit logging, refresh-token rotation, and a dedicated MySQL test container.
