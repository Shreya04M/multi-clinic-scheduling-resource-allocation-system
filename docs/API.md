# API contract

All protected routes use `Authorization: Bearer <JWT>`. Successful responses are JSON; validation failures are `422`, authentication failures `401`, authorization failures `403`, conflicts `409`, and unavailable vector services `503`.

| Method | Path | Purpose | Role |
|---|---|---|---|
| GET | `/health` | database health | public |
| POST | `/auth/register` | create a STAFF account, or an ADMIN-created account | public/ADMIN |
| POST | `/auth/login` | issue JWT | public |
| GET | `/auth/me` | return the authenticated safe profile | authenticated |
| GET | `/users` | list safe user profiles | ADMIN |
| GET | `/users/{user_id}` | retrieve a safe user profile | ADMIN |
| PATCH | `/users/{user_id}` | update email, role, or clinic | ADMIN |
| PATCH | `/users/{user_id}/status` | activate or deactivate a user | ADMIN |
| GET | `/dashboard` | aggregate statistics | authenticated |
| GET | `/appointments` | appointment list | authenticated |
| POST | `/appointments` | transactional scheduling | admin, doctor, receptionist |
| POST | `/notes` | create clinical note | admin, doctor |
| POST | `/notes/search` | authorized semantic search | authenticated |

`POST /appointments` accepts `patient_id`, `doctor_id`, `clinic_id`, `room_id`,
`appointment_date`, ISO `start_time` and `end_time`, and `equipment` as a list
of equipment IDs. The service validates doctor availability, clinic
association, room/doctor/equipment conflicts, and performs the appointment
plus equipment-link inserts in one transaction. A conflict is never
partially persisted.

Appointment IDs are generated by MySQL. Clinical-note IDs are also generated
by MySQL; the API retrieves the generated note ID after insertion.

The repository currently has no MySQL integration-test container. Unit tests
cover request validation and scheduling decision paths; live database
connectivity and SQL-object execution must be verified against a configured
MySQL 8.0.16+ instance.

`POST /auth/register` accepts `email`, `password`, `role`, and `clinic_id`.
Public registration creates clinic-scoped `STAFF` users only. An `ADMIN`
request requires an authenticated administrator. The first administrator can
be bootstrapped with a bcrypt hash:

```sql
INSERT INTO APP_USER (email, password_hash, role)
VALUES ('admin@example.com', '<bcrypt hash generated by backend/app/auth.py>', 'ADMIN');
```

`POST /auth/login` returns `{"access_token": "...", "token_type": "bearer"}`.
JWT claims include the user ID (`sub`), role, clinic scope, and expiry.
Password hashes are never returned by any endpoint.
